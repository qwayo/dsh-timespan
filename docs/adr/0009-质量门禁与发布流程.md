# 0009 质量门禁与发布流程

状态：已接受（2026-11-09）

## 背景

仓库此前没有任何 CI：PR #21–#26 的 `statusCheckRollup` 全为空，68 次提交里 58 次由 Agent 产生，合进 `master` 的唯一门槛是票面上手打的一句「npm test N/N 通过」。同时仓库是私有的，README 却在教人用 `github:qwayo/dsh-timespan` 安装。

已经发生的静默漂移：`src/host/rpc.js` 有 12 个方法，中英两版 README 的 RPC 契约表各只列了 11 个（漏 `queryDailySeries`）；`npm test` 与 `npm run check` 的文件清单是手写的，新增测试文件不写进脚本就不会被跑到；`assets/readme/structure.svg` 里写死了包名、版本号与测试文件数。

这个仓库的形态是：零依赖、零构建、`node --test` 跑 207 个测试约 0.9 秒、没有 lockfile、`client.js` 是手写源码而非构建产物。用户确认维持手写前端和现有测试形态。构建工具、JSX 编译、第三方 UI 库、CSS 框架及浏览器测试框架均超出当前工程边界。

## 决策

1. **CI 只做三件事**：`npm run check`（语法）、`npm test`（行为）、`node tools/ci-audit.mjs`（不变量）。不装任何依赖、不做构建、不跑 lint 与类型检查——后者需要 devDependencies 与 lockfile，与「零依赖零构建」的形态冲突，单独立项再议。
2. **不使用任何第三方 Action**（GitHub 官方维护的 `actions/checkout` 与 `actions/setup-node` 不在此列），包括 `dsh-plugin-checker`。理由：它只 `--dump-config` 验证 bundle 层挂上，不 boot Web、不验 `dsh.client`，而 Client 半才是本插件最容易坏的一面；`dshVersion` 默认 `latest` 会让上游发版无缘无故把 CI 判红；且它只有 1 star、数月未更新。加它会制造「已经被验证过」的虚假安全感。
3. **审计脚本守住十二类不变量**（`tools/ci-audit.mjs`）：bundle 清单、身份字符串三处一致、语法检查覆盖、测试发现、双语 README 对应、RPC 契约表、ADR 清单、配图成套、配图版本号、配图测试数、配图 ADR 数、README 配图可被插件市场抓取。选取标准只有一条——**错了不会报错、只会静默漂移**。
4. **Node 固定 24.16.0 单版本**，不用版本矩阵：零依赖的仓库没有需要兼容的依赖，多跑一档只是双倍等待。测试显式钉 `TZ=UTC`。
5. **触发条件是 PR 与 push 到 `master`**。仓库转公开后标准 runner 免费，双触发不增加成本，push 触发还能覆盖绕过 PR 直推的情况。
6. **分支保护先观察两周再设 required**：`test/dashboard.test.js` 里有一条 `performance.now() < 150ms` 的断言，在慢 CI 上有偶发失败风险，一上来设成 required 可能因偶发红把人卡住。
7. **发布是手动触发的 workflow**，不随 push 自动发。发布前重跑与 CI 完全相同的三条门禁，再用 OIDC Trusted Publishing 发 npm 并建 `v<version>` 标签与 GitHub Release。npm 版本不可覆盖，这是整条链上唯一不可回滚的动作，必须有人按。

## 后果

- 新增测试文件不再需要改 `package.json`：`npm test` 用 `test/*.test.js` 通配，Node 自己展开，跨平台一致。
- 改了源码文件忘记加进 `npm run check` 会红；加了测试文件会被自动跑到，但改了配图里的版本号或测试数没同步也会红。
- 改名这类动作会被「身份字符串三处一致」直接拦住——`package.json` 的 `name`、`cordis.patch.yml` 的 `name`、`client.js` 的模块 id 必须同时改。
- 发布仍然需要人工按一次，不会出现「改完版本号顺手 push 就发出去」。
- 这个决定不覆盖 UI 回归：真实 DSH 环境下的界面走查仍需人工做，CI 不替代它。
