# 界面语言改为插件设置项

状态：accepted
日期：2026-11-09

插件文案的语言由自己的设置项 `language` 决定，默认 `zh`，可选 `en`。它存在 Host `meta.settings` 里，和数字格式、侧栏显示时长一样是权威设置的一部分：`getSettings` / `setSettings` / `resetSettings` 与 `queryStats` 都带回它，Client 用它选字典。Client 不再用 `ctx.locale.bind(NS)` 取文案，改用本地的 `translate`（按 `language` 查插件字典，缺键回落中文，再缺就返回键名）；两套字典仍登记到宿主 locale 命名空间，点位上的 `locale: NS` 保持有效。切换语言时写 Host 并由语言订阅广播，让侧栏入口、仪表盘与设置页各自重渲染，页面不刷新。

理由是范围与一致性。用户要的是「这个插件能中英切换、默认中文」，而宿主的 `setLocale` 是全局偏好：在插件设置里调它，会连带换掉整个 DSH 的界面语言，等于让插件替别的产品面做决定。另一方面，语言和数字格式一样是「刷新后还要在、重启后还要在」的显示设置，放 Host 才有唯一权威副本；这也是既有的模式——Client 不缓存业务状态，每次读写设置时顺手落回来。

考虑过的替代方案：直接调 `ctx.locale.setLocale` 切全站，改动最小但影响面超出插件职责，且用户只是想换这个插件的文案；跟随浏览器或宿主语言而不提供开关，省掉设置项，但与「默认中文、设置里可切英文」的要求相反，也让中英混排的机器上行为不可预期；把语言存 `localStorage`，首屏无闪但形成第二份业务状态，多浏览器/多页面不同步，与「统计设置只存 Host」的既有边界冲突。

代价有三处：插件不再直接消费宿主 locale 的 `bind`，两套字典要自己维护一致（测试里加了键集合必须完全一致的断言，缺键会漏出中文或键名）；语言随设置出现在导出 JSON 里，勾选「恢复设置」导入时页面语言会跟着变；首屏在 `queryStats` 返回前仍按默认中文渲染，英文用户会看到一次极短的切换（首屏本来就在加载态，这里不上本地缓存来消掉它）。
